# 对商城侧（dujiao-next 发卡站）的对接要求

- 版本：v1.0（2026-09-19）
- 对接方式：**我们把账号系统作为"上游供货方"**，商城按下单流程调用我们的接口自动发货
- 配套文档：内部设计见 [shop-integration-design.md](./shop-integration-design.md)
- 全文只描述商城侧需要做/需要配置的内容；我们的接口实现由我方负责

---

## 1. 一句话说明

商城把我们的商品当**上游商品**上架销售；买家下单并支付成功后，商城调用我们的下单接口，我们**当场**为该买家的 Telegram 账号开通服务（建号 / 加天数 / 开白名单），然后由**我们的机器人通过 Telegram 私聊**把账号、密码、线路发给买家。

---

## 2. 连接配置（商城后台 → 站点连接）

| 配置项 | 填写内容 |
|---|---|
| 名称 | 任意（建议：`Sakura Emby`） |
| 协议（protocol） | **必须选 `dujiao-next`** |
| 站点地址（base_url） | 我方提供，例如 `http://127.0.0.1:8838`（同机部署）；若分机部署则为内网地址 |
| API Key | 我方提供 |
| API Secret | 我方提供 |
| 回调地址（callback_url） | **留空**（我们不需要向商城推送回调） |
| 重试次数 / 重试间隔 | 保持默认即可（正常不会触发） |
| 汇率 / 加价百分比 / 取整方式 | **不使用**（见 4.2 定价） |
| 状态 | 配置完成后在后台执行"测试连接"，应返回成功（我方 `ping` 接口） |

> 我方接口使用 HMAC-SHA256 签名（请求头 `Dujiao-Next-Api-Key` / `Dujiao-Next-Timestamp` / `Dujiao-Next-Signature`），这正是 dujiao-next 的标准上游协议，商城无需额外开发，只需按上表配置。

---

## 3. 需要商城能访问我们

- 商城的服务器必须能访问我方提供的 `base_url`（同机可用 `127.0.0.1`，跨机用内网地址 + 防火墙放行）。
- 我方只监听内网/本机地址，**不暴露公网**。
- 我方接口调用是**同步**的：商城发起下单请求后，我们会在同一次请求内完成开通并返回结果；商城侧对上游的超时是 30 秒，我们保证在超时内返回。

---

## 4. 商品上架

### 4.1 导入商品
1. 在商城后台的"上游商品"里，从该站点连接**同步/导入**我方商品。
2. 应看到 **2 个商品 / 4 个规格**：

| 商品 | 规格（SKU） | 说明 |
|---|---|---|
| 会员天数卡 | 30 天 / 90 天 / 180 天 | 可累加（买 2 份 30 天 = 60 天） |
| 永久白名单卡 | 永久 | 一次性开通，**不可退** |

3. 商品表单（TG ID）由我方下发，请在商城中**原样使用、不要修改字段、不要设为非必填**。

### 4.2 定价（重要）
- 我方所有商品的进货价返回为 **`0.00`**，**售价请全部在商城后台手工填写**。
- 请**不要开启"自动同步价格"**（否则会同步成 0 元）。
- 商城赚取售价与 0 元成本之间的全部差价，我方不参与分成、不做结算。

### 4.3 商品文案建议
商品详情页建议写明（避免售后纠纷）：
> 下单后由 Telegram 机器人自动开通并私聊发送账号信息。请务必填写**你自己的 Telegram 数字 ID**（可先与机器人对话后从机器人面板复制），填错将导致无法收到账号信息。

---

## 5. 下单与交付

### 5.1 表单
- 只采集一个字段：**Telegram ID**（纯数字，必填）。
- 请勿增加其它字段（不需要用户名、邮箱、备注）。

### 5.2 交付内容
- 我方返回给商城的"交付内容"只是**一句中性提示**（例："账号信息已通过 Telegram 发送"）。
- **请不要在订单详情页展示任何账号/密码类信息**——真实的账号、密码、线路、到期时间一律由我方机器人私聊发给买家。
- 商城订单页只需显示"购买成功"即可。

### 5.3 售后与失败处理（重要）
- 商城侧**不会**出现下单失败：我方对商城始终返回成功。
- 若买家填错 TG ID 或未与机器人对话过，买家将收不到 Telegram 消息 —— 这种情况由买家主动联系管理员，我方通过内部对账记录人工处理，**商城侧无需做失败提示、无需退款联动**。
- 白名单卡请在商品属性中设为**不可退款 / 不含售后**。

---

## 6. 订单与对账

| 要求 | 说明 |
|---|---|
| 订单号必须稳定 | 商城传给我们的订单号（`downstream_order_no`）是**幂等键**，重试时必须保持不变；不要用它之外的随机值 |
| 允许"处理中" | 商城订单在支付后会先进入"处理中/待发货"，约 30 秒后转为"已完成"（商城自身会向上游查询一次状态），这是正常现象 |
| 无需配置下游回调 | 我们不需要接收商城的订单回调，也不向商城推送 |
| 无需渠道 API / 礼品卡 | 本次对接不使用商城的"渠道 API""礼品卡""分销"等能力 |

---

## 7. 变更与联络

| 场景 | 处理方式 |
|---|---|
| 我们的接口地址 / 密钥变更 | 我方提前通知，商城后台同步修改 |
| 新增天数档位（如 365 天） | 我方商品接口增加规格后，商城重新同步商品并定价 |
| 商城需要新增商品字段 | 需先与我方确认（表单字段由我方下发） |
| 出现买家投诉未到账 | 商城提供**订单号 + 下单时间**，我方按对账记录核查 |

---

## 8. 商城侧验收清单

- [ ] 站点连接配置完成，"测试连接"成功
- [ ] 能同步到我方 2 个商品 / 4 个规格，且表单字段为 TG ID（必填）
- [ ] 售价已手工填写，**未开启**价格自动同步
- [ ] 白名单卡已设为不可退款
- [ ] 订单页不展示账号密码类交付内容（仅显示购买成功）
- [ ] 商城侧无失败订单处理逻辑（我方恒返回成功）
- [ ] 下单测试：填真实 TG ID 付款 → 约 30 秒后订单完成 → 买家在 Telegram 收到账号信息
